# Preflight Boolean Rule Validation Before Running Oris

## Purpose

Before running Oris on Boolean model ensembles generated by Gitsbe, users should run a preflight validation script to check whether any model contains Boolean rules that simplify to constant `TRUE` or `FALSE`.

This step is important because Oris relies on BooLEVARD/PyEDA during preprocessing. Some Boolean rules can be mathematically valid-looking but simplify to a constant value, which can cause BooLEVARD/PyEDA to fail or behave unexpectedly.

Examples:

```text
A | !A  ->  1  -> tautology / always TRUE
A & !A  ->  0  -> contradiction / always FALSE
```

The preflight script detects these cases before users submit expensive HPC jobs.

---

## Input structure

The script expects a folder containing ZIP files generated after the Gitsbe ensemble step.

Example:

```text
model_zips/
├── CACO2.zip
├── A549.zip
├── HT29.zip
```

Each ZIP file should contain Boolean model files inside a `Models/` folder:

```text
CACO2.zip
└── Models/
    ├── network_run_0__G5_M3.bnet
    ├── network_run_1__G2_M1.bnet
    └── ...
```

The `.bnet` files are expected to use a CSV-like format:

```text
targets, factors
EGFR, ( ABL1 | ERBB2 ) & ! ( CDK1 | MAPK14 )
JAK2, ( ABL1 | EGFR ) & ! ( PTPN6 | SIGNOR_PF1 )
```

The first column is the target node, and the second column is the Boolean rule.

---

## Running the preflight script

Activate the Python environment where the required dependencies are installed.

Required packages:

```bash
pandas
pyeda
```

Run:

```bash
python oris_preflight_rules.py model_zips --out preflight_results
```

If no output folder is provided, the script writes results to:

```text
preflight_results/
```

Optional debugging arguments:

```bash
python oris_preflight_rules.py model_zips --out preflight_results --limit-zips 2
python oris_preflight_rules.py model_zips --out preflight_results --limit-models 10
```

These options are useful for testing the script on a small subset before scanning the full ensemble.

---

## What the script checks

For every `.bnet` model inside every ZIP file, the script:

1. Reads the model directly from the ZIP file.
2. Parses each Boolean rule.
3. Converts Boolean syntax to PyEDA-compatible syntax.
4. Simplifies the rule.
5. Reports rules that simplify to:
   - `1`, meaning always TRUE / tautology
   - `0`, meaning always FALSE / contradiction
6. Continues scanning even if one model contains a problematic rule.

The script does not modify the models. It only reports potential issues.

---

## Output files

The script creates four output files.

### `oris_preflight_rule_issues.csv`

Contains one row per problematic rule.

Columns:

```text
zip_file
model_file
line_number
node
original_rule
normalized_rule
simplified_result
issue_type
error_message
```

Example:

```text
CACO2.zip, Models/network_run_0__G5_M12.bnet, 51, SIGNOR_C156,
( EGFR | ERBB3 | IGF1R | KDR | KIT | SIGNOR_C156 | TGFBR1 | !SIGNOR_C156 ),
1,
tautology
```

### `oris_invalid_models.csv`

Lists models that contain at least one problematic rule.

Columns:

```text
zip_file
model_file
model_id
n_issues
```

A model is considered invalid if it contains a tautology, contradiction, or parse error.

### `oris_valid_models.csv`

Lists models without detected Boolean rule issues.

Columns:

```text
zip_file
model_file
model_id
```

This file can later be used to decide which models are safe to process with Oris.

### `oris_preflight_summary.csv`

Contains summary metrics.

Example:

```text
metric,value
n_zip_files_scanned,7
n_models_scanned,1022
n_rules_checked,85848
n_issue_rules,1002
n_invalid_models,1002
n_valid_models,20
n_parse_errors,0
```

## Example issue found during testing

During testing, the preflight script scanned 7 ZIP files and 1022 Boolean models. It found 1002 problematic rules and 1002 invalid models.

The issue was concentrated in one repeated rule for the node `SIGNOR_C156`:

```text
SIGNOR_C156 = EGFR | ERBB3 | IGF1R | KDR | KIT | SIGNOR_C156 | TGFBR1 | !SIGNOR_C156
```

Because the rule contains both:

```text
SIGNOR_C156
```

and:

```text
!SIGNOR_C156
```

connected by OR, this part of the rule simplifies to:

```text
SIGNOR_C156 | !SIGNOR_C156 = 1
```

Therefore, the full rule simplifies to:

```text
SIGNOR_C156 = 1
```

This means the node is always ON, regardless of its regulators.

---

## Biological/source-network interpretation

The problematic node was identified as:

```text
SIGNOR_C156 = PIK3R1, PIK3CA
```

This corresponds to the PI3Kalpha complex, where:

```text
PIK3CA = catalytic PI3K subunit
PIK3R1 = regulatory PI3K subunit
```

Inspection of the SIF file used before Gitsbe ensemble generation showed conflicting self-regulation:

```text
SIGNOR_C156 -> SIGNOR_C156
SIGNOR_C156 -| SIGNOR_C156
```

This means the same node was represented as both activating and inhibiting itself. When converted into a Boolean rule, this created:

```text
SIGNOR_C156 | !SIGNOR_C156
```

which is a tautology.

## Recommended user actions

If the preflight script reports only a small number of invalid models, users may choose to skip those models before running Oris.

However, if most models are invalid, users should not run Oris directly. Instead, they should inspect the source network used before Gitsbe ensemble generation.

Recommended workflow:

1. Run the preflight script after Gitsbe ensemble generation.
2. Check `oris_preflight_summary.csv`.
3. If invalid models are found, inspect `oris_preflight_rule_issues.csv`.
4. Check whether the same node or rule appears repeatedly.
5. If the issue is repeated across many models, inspect the original SIF/network file.
6. Resolve conflicting edges upstream.
7. Regenerate the Gitsbe ensemble.
8. Run the preflight script again.
9. Run Oris only after the rule issues are resolved or intentionally accepted.

For the `SIGNOR_C156` example, the recommended first fix is to remove the contradictory self-loop edges from the SIF file:

```text
SIGNOR_C156 -> SIGNOR_C156
SIGNOR_C156 -| SIGNOR_C156
```

This is the least opinionated fix because it avoids choosing whether positive or negative autoregulation is biologically correct.

After removing the conflicting self-loops, the ensemble should be regenerated and checked again with the preflight script.

## Future improvements

Future versions of the preflight workflow could add:

1. A summary of the most frequent problematic nodes.
2. Detection of candidate media/input nodes.
3. Detection of output/sink nodes.
4. An option for Oris to skip invalid models automatically.
5. A strict mode that stops Oris if any invalid models are detected.
6. Optional export of simplified models, with strong user warnings.

For now, the preflight rule validator already provides a useful safety check between Gitsbe and Oris.
